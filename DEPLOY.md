# Deploying — free hosting on Render

The whole product runs as **one** container: the [Dockerfile](Dockerfile) builds
the React app and hands the output to FastAPI, which serves the UI, the API and
the docs from a single HTTPS origin. There is nothing to configure for CORS and
nothing to keep in sync between two deployments.

```
GitHub push to main
   -> Render pulls the repo
   -> Docker stage 1: npm ci && npm run build   (frontend/dist)
   -> Docker stage 2: pip install + copy dist -> /app/static
   -> uvicorn app.main:app on $PORT
                |
                +-- MongoDB Atlas (unchanged)
```

Cost: **₹0**. Render's free web service plus the Atlas M0 free cluster you are
already using.

---

## 1. Push the deployment files

```powershell
git add Dockerfile .dockerignore render.yaml DEPLOY.md .github/workflows/azure-deploy.yml
git commit -m "Add Docker + Render deployment"
git push
```

## 2. Let Atlas accept connections from Render

Render's free tier does not give you a fixed outbound IP, so the cluster has to
accept connections from anywhere. Atlas → **Network Access** → **Add IP Address**
→ **Allow access from anywhere** (`0.0.0.0/0`).

That is safe only because the database still requires the username and password
in your connection string — but it does mean that password is the single thing
protecting your data. If it has ever been shared or pasted anywhere, rotate it
now under **Database Access** before continuing.

## 3. Create the service

1. Sign in at [dashboard.render.com](https://dashboard.render.com) with GitHub.
2. **New +** → **Blueprint**.
3. Pick the `sahjaaswieducationaltrust/student-management` repository. Render
   reads [render.yaml](render.yaml) and proposes one service,
   `hellokids-school-management`.
4. It will prompt for the values that are deliberately **not** in the repo:

   | Variable | What to enter |
   | --- | --- |
   | `MONGODB_URI` | Your Atlas connection string, exactly as in `backend/.env` |
   | `ADMIN_PASSWORD` | A strong password — see the warning below |
   | `ADMIN_EMAIL` | The admin login email from your `backend/.env` |
   | `ADMIN_NAME` | The admin's display name from your `backend/.env` |
   | `SCHOOL_ADDRESS` | Your branch address (prints on every receipt) |
   | `SCHOOL_PHONE` | Your branch phone |
   | `SCHOOL_EMAIL` | Your branch email |

   `JWT_SECRET` is generated by Render automatically. Everything else is already
   set in `render.yaml`.

5. **Apply**. The first build takes 5–8 minutes (npm install plus pip install).

When it finishes you get a URL like `https://hellokids-school-management.onrender.com`:

| Path | What it serves |
| --- | --- |
| `/` | The React UI |
| `/api/health` | Health check — should return `{"status":"ok", ...}` |
| `/docs` | Swagger API docs |

Every later `git push` to `main` redeploys automatically.

---

## Before you hand the URL to anyone

**Change the admin password.** The admin account already exists in your Atlas
database, created on an early local run with a weak development password.
Setting a strong `ADMIN_PASSWORD` on Render does **not** fix this —
`bootstrap_admin()` in [backend/app/main.py](backend/app/main.py#L20-L35) only
creates the account when the `users` collection is empty, so the existing
password stays live. Log in and change it from inside the app, or update the
user document in Atlas directly. Do this before the URL reaches anyone.

**`/docs` is public.** Anyone with the URL can browse the full API surface. The
endpoints themselves are behind JWT auth, so this leaks the shape of the API
rather than any data — but if you would rather it were closed, pass
`docs_url=None, redoc_url=None` to `FastAPI(...)` in `backend/app/main.py`.

## Known limits of the free tier

- **It sleeps.** After 15 minutes with no traffic the container is stopped. The
  next request wakes it, which takes roughly 50 seconds. For a demo that is
  fine. For a front desk that opens the app each morning it is genuinely
  irritating, and the fix is either Render's Starter plan (~₹500/month, no
  sleeping) or an Oracle Cloud Always Free VM (free forever, but you administer
  the VM yourself).
- **512 MB RAM, 0.1 CPU.** Ample for this app — a single uvicorn worker holding
  a Mongo connection pool sits well under the limit.
- **No disk.** Nothing is persisted in the container. Receipts are generated in
  memory by reportlab and streamed to the browser, so this costs you nothing
  today — but if you ever add file uploads (student photos, documents), they
  will vanish on every redeploy. Use Atlas GridFS or an object store for those.
- **750 instance-hours/month** across all free services. One service is fine.

## Rolling back

Render → the service → **Events** → pick an earlier deploy → **Rollback**.
Or revert the commit and push; the redeploy is automatic either way.

## The Azure workflow

[.github/workflows/azure-deploy.yml](.github/workflows/azure-deploy.yml) does
the same job — build the frontend, fold it into the backend, ship one App
Service — but it is now **manual-only** (`workflow_dispatch`). It needs an App
Service to exist and an `AZURE_WEBAPP_PUBLISH_PROFILE` repository secret;
without those it fails, and on a `push` trigger it would fail on every commit.
Restore the trigger if you move to Azure. Azure's F1 Free tier is capped at 60
CPU-minutes per day, which is why Render is the better free option here.

## Running the container locally

Worth doing once before you push, so a broken build shows up on your machine
rather than in a Render log:

```powershell
docker build -t hellokids .
docker run --rm -p 8000:8000 --env-file backend/.env hellokids
```

Then open <http://localhost:8000>. `$PORT` defaults to 8000 inside the image, so
no extra flags are needed.
